# Jinix Jupiter — Milestone 6 DMA Architecture

## 1. Scope

Milestone 6 introduces Jupiter's first functional direct-memory-access engine.

The selected initial implementation is intentionally small and deterministic.
It provides one CPU-controlled channel for aligned 32-bit copies between
locations in Jupiter external SDRAM.

This document defines the Milestone 6 DMA contract before RTL implementation.

It does not claim Quartus synthesis success, timing closure, FPGA resource
utilization, measured throughput, or operation on physical hardware.

## 2. Selected Initial Feature Set

The Milestone 6 DMA implements:

- one DMA channel;
- external-SDRAM to external-SDRAM copies;
- 32-bit transfer granularity;
- source address auto-increment by four bytes;
- destination address auto-increment by four bytes;
- transfer length expressed in 32-bit words;
- CPU-controlled start;
- CPU-readable busy and completion state;
- one outstanding DMA memory transaction at a time;
- deterministic participation as a third external-SDRAM master.

The initial implementation does not include:

- multiple DMA channels;
- simultaneous independent DMA channels;
- descriptor chains;
- scatter/gather;
- linked lists;
- peripheral-triggered transfers;
- audio-triggered transfers;
- GPU-triggered transfers;
- interrupts;
- burst transactions;
- fill operations;
- fixed-source or fixed-destination modes;
- byte or halfword transfer modes;
- stride or rectangular-copy modes;
- overlapping-copy or memmove semantics;
- address translation;
- cache coherency behavior.

Those features are not required for Milestone 6 completion.

## 3. CPU-Visible DMA MMIO

Milestone 6 selects the CPU-visible DMA control aperture:

    0x00001200 - 0x000012FF

This follows the existing Milestone 5 GPU aperture at
`0x00001100 - 0x000011FF`.

The selected initial register layout is:

| Address | Register | Access | Meaning |
| --- | --- | --- | --- |
| `0x1200` | `CONTROL` | W | Bit 0 = START |
| `0x1204` | `STATUS` | R | Bit 0 = BUSY, bit 1 = DONE |
| `0x1208` | `SRC_BASE` | R/W | First source byte address |
| `0x120C` | `DST_BASE` | R/W | First destination byte address |
| `0x1210` | `LENGTH_WORDS` | R/W | Number of 32-bit words to copy |

Unused aligned offsets within the DMA aperture read as zero and ignore writes.

`CONTROL` is write-only and reads as zero.

Writes to `STATUS` are ignored.

Configuration registers honor the transaction byte-write strobes.

## 4. Start and Completion Semantics

A write of one to `CONTROL.START` while the DMA is idle snapshots:

- `SRC_BASE`;
- `DST_BASE`;
- `LENGTH_WORDS`.

The active transfer uses only these snapshots.

Software may modify the live configuration registers while a transfer is
busy without changing the active transfer.

A START request while BUSY is asserted is ignored.

Starting a nonzero transfer:

- clears DONE;
- asserts BUSY;
- begins with a source read.

When the final destination write completes:

- BUSY clears;
- DONE asserts.

DONE remains asserted until:

- another accepted START clears it; or
- reset clears it.

A transfer with `LENGTH_WORDS == 0` completes immediately without issuing a
memory transaction:

- BUSY remains clear;
- DONE asserts.

No interrupt is generated by the initial implementation.

## 5. Address Requirements

The initial DMA operates only on the established external-SDRAM maximum
aperture:

    0x10000000 - 0x17FFFFFF

Source and destination addresses must be aligned to four bytes.

The initial DMA does not provide overlapping-copy semantics. Software must
not request a transfer whose source and destination ranges overlap when the
result would depend on memmove-style ordering.

Installed-capacity enforcement remains the responsibility of the established
SDRAM frontend. Addresses beyond reported installed SDRAM capacity retain the
existing deterministic unavailable-memory behavior.

Milestone 6 does not permanently partition external SDRAM for DMA use.

## 6. Transfer Sequencing

For each 32-bit word, the initial DMA performs:

1. one aligned 32-bit source read;
2. captures the completed read data;
3. one aligned 32-bit destination write;
4. increments the active source address by four;
5. increments the active destination address by four;
6. decrements the remaining-word count.

The DMA does not issue the destination write before the corresponding source
read has completed.

While either request is stalled, the DMA keeps all request fields stable.

Only one DMA memory transaction may be outstanding.

The captured read word remains stable until its destination write completes.

## 7. External-SDRAM Master Interface

The DMA uses the same logical 32-bit valid/ready transaction contract as the
existing CPU and GPU external-SDRAM masters:

- `valid`;
- `write`;
- 32-bit byte address;
- 32-bit write data;
- four byte write strobes;
- 32-bit read data;
- `ready`.

DMA writes use all four byte strobes:

    4'b1111

The DMA master connects before `jupiter_sdram_frontend`.

The existing frontend continues to convert each logical 32-bit transaction
into the required pair of physical 16-bit SDRAM operations.

## 8. Three-Master Arbitration

Milestone 5 established CPU and GPU as two external-SDRAM masters.

Milestone 6 adds DMA as the third external-SDRAM master.

The selected policy is deterministic, non-preemptive, three-way round-robin
arbitration among:

1. CPU;
2. GPU;
3. DMA.

A granted request remains selected until the shared SDRAM frontend asserts
ready. A requester may not be preempted in the middle of one logical 32-bit
transaction.

When two or three masters are waiting at a free arbitration point, selection
proceeds cyclically after the most recent completed contested winner:

    CPU -> GPU -> DMA -> CPU

Inactive requesters are skipped.

After reset, CPU is the first preferred requester when CPU participates in
the first contested arbitration.

A transaction that begins uncontested does not change contested
round-robin history.

The exact number of wait cycles is not an architectural performance
guarantee.

SDRAM refresh remains controller maintenance rather than a fourth Jupiter
master.

## 9. CPU MMIO Versus DMA Data Traffic

CPU accesses to the DMA control aperture are ordinary interconnect MMIO
transactions.

DMA control-register accesses do not themselves pass through the external
SDRAM arbiter.

Only DMA source reads and destination writes participate as DMA-master
transactions in the shared SDRAM arbiter.

The CPU may therefore configure an idle DMA engine without consuming a DMA
data-master grant.

## 10. Deterministic Verification Plan

Milestone 6 verification must include:

1. reset state;
2. register read/write behavior;
3. byte-write-strobe behavior for configuration registers;
4. zero-length immediate completion;
5. START snapshot behavior;
6. busy START rejection;
7. stable source-read request under stalls;
8. correct captured source data;
9. stable destination-write request and data under stalls;
10. exact source and destination increment behavior;
11. exact requested word count;
12. DONE/BUSY completion behavior;
13. deterministic multiword SDRAM-to-SDRAM copy;
14. source preservation;
15. unrelated-memory guard preservation;
16. CPU-visible DMA configuration and status;
17. CPU/DMA contention;
18. GPU/DMA contention;
19. simultaneous CPU/GPU/DMA contention;
20. progress by all requesting masters under the selected arbitration policy;
21. integration through the existing SDRAM frontend/controller/model;
22. regression of previously verified CPU, GPU, SDRAM, and wrapper behavior.

A small deterministic source pattern and destination region should be used so
every copied word can be checked exactly.

## 11. Milestone 6 Acceptance Boundary

Milestone 6 establishes a useful general external-memory copy engine and the
three-master SDRAM architecture needed to support it.

Milestone 6 does not establish:

- DMA hardware throughput;
- burst-transfer performance;
- audio streaming DMA;
- GPU-command-triggered DMA;
- descriptor processing;
- completion interrupts;
- overlapping-copy semantics;
- Quartus timing closure;
- FPGA resource utilization;
- physical-hardware success.

Those claims require later design decisions or actual synthesis/hardware
evidence.
